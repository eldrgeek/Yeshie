# chatgpt.com automation repair — 2026-07-08

Mike Wolf + Claude (Opus 4.8, CCc). Repair pass on `01-submit-prompt` after the
BYOA-bridge POC (2026-07-07) found it silently reporting `{"status":"ok","value":""}`
— success, but nothing typed.

## TL;DR

The stock recipe was broken by **three** independent things (not the two hypotheses in
the original ticket — `chrome.debugger.attach` was never the problem; it worked every time):

1. **Selector drift, Lexical → ProseMirror.** The composer is now
   `div#prompt-textarea.ProseMirror`, `aria-label="Chat with ChatGPT"`, with **no**
   `data-testid` and **no** `data-lexical-editor`. Every old anchor was dead, and the
   `div[contenteditable='true']` fallback was actively wrong — rendered messages are
   *also* ProseMirror contenteditable divs sitting earlier in the DOM, so `querySelector`
   grabbed a message, not the composer.
2. **Enter no longer submits.** A CDP-dispatched Enter is now a **no-op** on ChatGPT's
   ProseMirror (verified: text stays in the composer, nothing sends). `trustedType(submit=true)`
   typed fine but never submitted → the read returned empty → false success.
3. **Wrong tab.** The chain had no `navigate`/`open_tab` step, so with `tabId:null` the
   extension auto-picked the active tab of the last-focused window (usually not ChatGPT)
   and ran against the wrong page.

Two more issues surfaced while verifying the fix end-to-end:

4. **`:last-of-type` read is wrong for multi-turn.** Verified against a real 5-turn
   conversation: `[data-message-author-role='assistant']:last-of-type` returned an
   *earlier* turn, because each turn is its own wrapper and `PRE_GUARDED_READ` uses
   `querySelector` (first match in document order). Only correct on a single-turn chat.
5. **Thinking-model completion race.** `wait_for [data-testid='stop-button']` invisible
   fires too early for `gpt-5-*-thinking`: the stop button toggles off during the
   think→answer transition, so the read captured an empty `result-thinking` container.

## Fixes (all inner-loop — model JSON only, no extension rebuild)

`sites/chatgpt.com/tasks/01-submit-prompt.payload.json`:
- `prompt_input` retargeted to ProseMirror: `match.name_contains=["Chat with ChatGPT"]`,
  `anchors.ariaLabel="Chat with ChatGPT"`, fallbacks scoped to the `#prompt-textarea` id.
  Wrong-tab now fails **loudly** (`Cannot resolve: prompt_input`) instead of silently.
- New `send_button` target (`[data-testid='send-button']`, aria "Send prompt").
- Chain: `assess_state` (MUST stay `chain[0]` — it's what makes startRun skip its
  pre-chain auth-wait; a non-assess first step times out with "user did not complete
  login") → `navigate {{base_url}}` (fresh single-turn chat; makes the read correct) →
  `type submit:true` (Enter is a harmless no-op; keeps text intact — `submit:false` makes
  trustedType press Tab, which lost the send button) → `click send_button` (the real
  submit) → `wait_for [data-testid='copy-turn-action-button']` visible (the reliable
  "answer fully rendered" signal; supersedes the racy stop-button) → `read`.

`sites/chatgpt.com/site.model.json`:
- framework `react-lexical` → `react-prosemirror`; prompt_input, response_container, and a
  new `generation_complete` target documented with the gotchas above.

## Verification status (honest)

Proven independently this session, each against the live logged-in ChatGPT via CDP
(port 9222, ChromeMain):
- Type resolves via `[aria-label="Chat with ChatGPT"]` / `#prompt-textarea` and inserts
  text (mutationCount 15–49). ✓
- Send-button click submits: composer clears, stop-button appears, URL → `/c/…`, an
  assistant message is created. ✓ (also a full 9-step relay run returned success with the
  send_button resolved + clicked)
- `read` textContent extraction returns the answer on a completed message ("Received."). ✓
- `:last-of-type` returns an earlier turn on a 5-turn conversation (→ single-turn is
  required). ✓
- `copy-turn-action-button` present only on completed messages, absent during thinking. ✓

**Not** cleanly captured in a single automated run: the full
type→submit→wait→read→token. Blocked by environment state, not recipe logic. The
specific blocker is **ChatGPT temporary-chat mode**:
- It was inadvertently toggled ON during testing (verified: the composer header toggle
  read "Turn off temporary chat"). I turned it back OFF (restored) and confirmed a
  `navigate` to chatgpt.com/ then stayed normal (`temporary-chat=false`, composer
  present).
- BUT on the very next recipe run, the tab was back at `?temporary-chat=true` with the
  conversation wiped (0 user + 0 assistant messages) even though `type` and `click`
  both reported ok. So **something in the automated navigate→type→submit cycle
  re-engages temporary chat and discards the ephemeral conversation** before the answer
  renders. Leading hypotheses: a residual account/server-side temp preference that a
  full-page load restores, or a keystroke in the type step hitting ChatGPT's
  temporary-chat shortcut. Not yet isolated.
- Also compounding: the default model was `gpt-5-5-thinking`, slow and likely throttled
  after ~14 rapid test submissions this session.

**Update — temporary chat is an account-level default, and it's the hard blocker.**
Repeated runs confirmed: `navigate` to chatgpt.com/ re-enters Temporary Chat even after
the composer toggle is switched off, and even when the pre-type state reads "normal" the
tab flips back to `?temporary-chat=true` and discards the conversation (0 user + 0
assistant messages) mid-run. The composer toggle only suppresses it transiently; the
account keeps defaulting to temporary. Ephemeral temp submits never persist a readable
answer, so `read` returns null every time. Compounded by a slow/throttled
`gpt-5-5-thinking` model after ~16 rapid test submissions this session.

**Defenses added to the recipe** (so it never silently submits into an ephemeral chat):
- `s2a` **self-heal**: `assess_state` detects the "Turn off temporary chat" toggle and,
  via `onMismatch: branch:disable_temp`, clicks it off — returning to a fresh normal
  chat. No-op/safe on accounts where temp is already off ("Turn on temporary chat"
  present → state matches, no branch). A `s2-settle` delay precedes it so the check
  doesn't race SPA hydration.
- `s2b` **fail-fast guard**: `wait_for` a negative-lookahead URL that never matches
  `?temporary-chat=true`, so a still-temporary chat errors in 8s instead of hanging 180s.

**What's needed to go fully green (only Mike can do the account part):** disable
Temporary Chat at the ChatGPT **account/settings** level (not just the composer toggle),
then run once on a rested account. Every mechanical link is already proven; this is the
last environmental gate.

## Caller contract (important)

Run this recipe with an explicit `tabId` = an already-authenticated chatgpt.com tab
(resolve via `GET /tabs/list`). Do **not** rely on tabId auto-discovery. The recipe does
NOT open its own tab: a cold-opened chatgpt.com tab intermittently redirects to `/login`
(unauthenticated), so the composer never mounts.

## Recommended follow-ups (outer-loop — need `wxt build` + extension reload)

1. **startRun tab discovery** (`packages/extension/src/entrypoints/background.ts`
   ~L2681): when no `tabId` is passed and `params.base_url` is set, prefer a tab whose
   host matches `base_url` over the arbitrary active tab. This kills the silent
   wrong-tab class for **every** site recipe, not just chatgpt. Conservative: only
   changes behavior in the currently-broken case (active tab ≠ base_url host and a
   base_url-host tab exists).
2. **A `wait_for` "text stable / non-empty" mode** (or `read` that polls until the
   matched element's text is non-empty and stable). Would make response capture robust
   without depending on site-specific completion selectors like `copy-turn-action-button`.
3. Consider a `read` "last match" mode (`querySelectorAll(sel).pop()`) so multi-turn
   reads work without forcing a fresh conversation.
