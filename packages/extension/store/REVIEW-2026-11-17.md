# Yeshie extension: code review before the Chrome Web Store

_2026-11-17. Mike Wolf asked for a detailed review, cleanup and store preparation by an Opus 5.5 instance; this is that review, by Claude Opus 5.5 in the SOMA Rooms thread "SR: Prepare Yeshie for the Chrome Web Store". Scope: `packages/extension` on `master` at `175db81` (about 6,000 lines of TypeScript, of which `src/entrypoints/background.ts` is 4,300)._

Prior art: SOMA Guide's store preparation in `eldrgeek/soma-rooms` `packages/guide-extension` (CHANGELOG with store column, 132-character description, unlisted first release). Chrome Web Store program policies (single purpose, minimum permissions, no remotely hosted code, limited use of user data).

## Checked and fine for the store

- **No remote code.** Every function run in a page is bundled (`PRE_*` functions via `chrome.scripting.executeScript`, fixed `Runtime.evaluate` templates with `JSON.stringify`-quoted selectors). The `js` payload action does not evaluate its `code`; `PRE_RUN_DOMQUERY` matches keywords in it and runs bundled logic. Payloads are data.
- **Debugger use** is limited to `Input.insertText`, `Input.dispatchKeyEvent`, `Input.dispatchMouseEvent` and fixed `Runtime.evaluate` click/lookup templates, on the tab a task targets, detached after the chain.
- **Recording** captures clicks and typed values only while the user toggles it, shows a red REC badge, and skips password fields.
- **No external network.** The store build talks to `localhost` only (relay `:3333`, recorder bridge `127.0.0.1:27184`).

## Not fixed (follow-ups, none blocks an unlisted release)

1. **The relay trusts any local client.** Anything that can listen on `localhost:3333` can drive the browser. For Mike's machines that is acceptable (local malware already owns the machine). Before Yeshie goes to people outside the estate, add pairing: the relay shows a code, the side panel stores it, the socket handshake carries it.
2. **The relay's default profile is Mike's address** (`packages/relay/instances.js` `DEFAULT_PROFILE`). Anyone else's relay refuses untargeted jobs until they set `YESHIE_DEFAULT_PROFILE`. The reviewer instructions pass a tab target to avoid it. Make the default "the only connected profile" when exactly one is connected.
3. **`background.ts` is 4,300 lines in one closure** with YeshID-specific defaults (`DEFAULT_BASE_URL = https://app.yeshid.com`, the teach overlay's `matches`, offboarding keywords in `PRE_RUN_DOMQUERY`). It works and is covered by 1,480 unit tests; splitting it is a refactor for its own PR.
4. **Side panel says "start a Claude listener session"** when no listener is polling. A store user without the estate's listener needs a plainer message and a setup link.
5. **Two copies in one Chrome profile.** If Mike installs the store build next to the unpacked personal build, both connect to the relay as separate instances. Keep the store build in profiles that do not have the personal one.

## Verification

- `npm test` (CI's set): 54 suites, 1,480 tests pass, including the new `tests/unit/store-readiness.test.ts` (7 tests guarding findings 1 and 2, the store's text limits and a justification for every permission).
- Store zip built (`yeshie-extension-1.0.0-chrome.zip`, 71 KB), loaded into Chromium with the real relay: navigate, debugger typing, click and read all `ok` (`"out": "Hello Store"`); `/tabs/list` returns web tab URLs; a page posting the old bridge message gets no reply.
- Leak guard: a store build with a test token in `.env` and a line logging it fails with "Store build refused: … contains the SOMA admin token".
